## 1. PROBLEM STATEMENT

Seven (7) compounding gaps are blocking realworldcerts.com from operating as a measurable, trustworthy, provable customer-to-cash engine:

1. **Product intangible (buyer blind)**: All 37 catalog entries report `lectureCount=0`, `quizCount=0`. No buyer can (a) run a real sample quiz with explanations, (b) read a preview lesson, or (c) see distinctive, verifiable course artwork before paying. Buyers purchase on description-only trust — which suppresses conversion and raises refund risk.
2. **Funnel unmeasured (guessing at bottlenecks)**: The site has catalog pages, course pages, 5 checkout pages, and a `/api/orders` POST. Today no durable 8-stage event store records `catalog_view → course_page_view → checkout_start → payment_attempt → verified_payment → successful_delivery → refund → abandoned_order` with a JOIN-able RWC order reference. Prioritization is by guess, not by drop-off-percentage evidence.
3. **P0 public repo security (tracked sensitive material)**: The git worktree and history contain (verified): `audit/legal/HUISSIER_MANDAT_INFO_SECURE.pdf` (legal PDF), nine `.ps1` operational scripts with credential-loading logic / DPAPI vault references / Doomsday Vault runbooks, and a `CHANGELOG.md` with 30+ explicit references to RIB 182/372, Banking Circle 646, EIP-55 L2 wallet `0xA46225a984E2B2b5E5082E52AE8d8915A09FEFE7`, and Attijari Agence 018 litigation coordinates. No git-history scrub has been performed; deleting files in one commit does NOT remove them from historical clones. Credential rotation + secret-manager migration is incomplete.
4. **P1 no reliable build-deploy pipeline (production un-gated)**: `package.json` defines 52 scripts including `lint`, `typecheck`, `test` (Vitest 193/193 PASS), `build` (prisma generate + next build), `audit:truth` — however `.github/workflows/` contains 16 files (deploy-vercel, vault-sync, org-secret-sync, guard-repo-integrity, anti-regression, autonomous-scheduler, swarm-tick, devops-self-healing, secret-scan, owner-payout, owner-crypto-withdraw, org-broadcast, self-launch, deploy-space-z, deploy-pages, sync-secrets) **but no `ci.yml`** that deterministically chains `npm ci → lint → typecheck → vitest → prisma generate → next build → smoke health → artifact` on EVERY pull request and push to `main`/`release`. Current `deploy-vercel.yml` runs `checkout → node22 → install Vercel CLI → pull → provision OWNER vars → deploy` with **no lint/typecheck/test/build pass gate**. Deployed commit SHA is not post-verified against a `/health` endpoint; rollback script/provenance not proven.
5. **P1 settlement not bound to provider evidence (completion by agent-assertion risk)**: Prisma schema has `Payout.providerTransactionId`, `PayoutItem.externalRef`, `TransactionLog.providerTxId`, `OwnerSettlement.referenceId` — but **no `@unique` database index** on any provider transaction column (idempotency duplicate-injection risk). All payout/sale/event status columns use loose `String @default("pending")` — no **Postgres native ENUM** for 5 distinct states (`initiated/pending/completed/failed/needs_manual_proof`), no **CHECK constraint forbidding status reversal** (e.g. completed → pending), and no **Postgres trigger function** that literally raises an error when `SET status='completed'` without a non-empty `provider_raw_payload JSONB` and `provider_signature TEXT`. Reconciliation is partial (`ExternalPayerEnforcer.mjs` scans settled_externally_pending vs registry) but does not call every provider's authoritative balance+last-7-days endpoint daily and flag discrepancies >0.01 USD.
6. **P1 sales engine not separated from payout engine (agent-fabrication-of-revenue risk)**: One package, one schema, one set of DB grants today. `RevenueEvent`, `Payout`, `OwnerSettlement`, `TransactionLog` live together — no physical table or DB-role separation between (i) the Next.js web process writing customer sales and (ii) the owner hands-free PowerShell wrapper writing owner payouts. The traceable chain `Product → Order → Verified payment → Course delivery → Ledger entry → Reconciliation → Eligible payout → Provider confirmation` has gaps at 5 of the 7 intermediary JOINs today. Marketing/inbound scripts can today modify status-like fields without a DB-role `GRANT` restriction, creating a structural path where a "revenue" write is synthetic.
7. **P2 no single authoritative operational status (dashboard drift risk)**: Truth sources today = `data/out/*` signed NDJSON manifests, preflight JSON reports, `.jsonl` orders, swarm HMAC chain, `audit/*` markdown reports, daemon state JSON, procurement/PO JSON, settlement JSON. No file is designated `AUTHORITATIVE_LEDGER` with the rule "all other status files are DERIVED readers that REFRESH FROM AUTHORITATIVE, NEVER WRITE THEIR OWN FACTS". Schema validation (JSON Schema / z-schema) does not run ON EVERY append. State transitions are not documented as a finite DFA. This allows two independently-maintained reports to disagree — creating wrong settlement decisions.

Each gap is addressed by a vertical S-slice below. Fail-closed is doctrine everywhere.

- **7a** File format: Append-only NDJSON (newline-delimited JSON). One event per line. No update, no delete, no reordering. The append function: (1) locks file, (2) reads last line to get `prevHmac`, (3) validates event schema, (4) computes `currHmac`, (5) appends + fsync, (6) releases lock. Any step 1–5 failure → raises.
- **7d** DERIVATION RULE (CRITICAL NON-NEGOTIABLE): All other status files / reports / dashboards today (preflight JSON reports, swarm manifest NDJSONs, audit markdown reports, daemon state JSON, PO JSON, individual settlement JSON files) are HEREBY RECLASSIFIED AS DERIVATIONS.
